# ADR 0027: Pluggable Provider runtime boundary

Date: August 18, 2026

## Status

Accepted

## Context

HCAI CHAT already persisted Provider profiles and immutable per-mode model-route revisions, but the generation service still selected only `local_test` profiles and executed a hard-coded local output function. Admin therefore could describe future Providers without the worker being able to execute them. Route retry and timeout fields were also not applied to queued jobs.

Real Provider credentials and paid-call authority are not available in this workspace. The product must remain useful locally and fail closed in production while making the next integration additive instead of requiring changes to billing, jobs, Assets, provenance, or Admin routing.

## Decision

- Generation runtimes implement `creation.ProviderRuntime` and identify one Provider plus their exact supported mode/model capabilities.
- `RuntimeCatalog` is the only execution lookup. Submission, retry, Admin enablement, and model-route activation all require an exact `(provider, mode, model)` capability match.
- The API and worker receive catalogs built from the same process configuration. Credentials remain private to a runtime implementation and are never persisted in a generation, job payload, audit event, or API projection.
- A generation snapshots the active Provider, model, immutable route revision, and route version. Its durable job inherits that revision's maximum attempts. The worker applies that revision's timeout to the Provider call.
- Provider outputs cross a closed typed media contract before any Asset is inserted: UTF-8 text, JPEG/PNG image, MP4 video, or WAV audio, with a 100 MiB ceiling and required visual dimensions.
- Provider failures cross a closed safe-code boundary. Unknown upstream errors become `provider_request_failed`; raw responses and request identifiers are not written to user-visible generation evidence.
- Generated bytes are atomically persisted by the creation service. Cancellation, duplicate delivery, credit capture/release, notification, audit, Webhook, and orphan-file cleanup remain inside the existing transaction boundaries.
- The generic durable job kind is `generation.generate`; migration `0035_provider_runtime_boundary` upgrades queued historical local jobs in place.
- The deterministic local runtime remains the only configured runtime until a Provider is explicitly selected, credentials are supplied outside the repository, paid calls are authorized, and staging acceptance passes.

## Consequences

- Registering a runtime is not enough to serve traffic. Its database profile must also be enabled and activated through an audited immutable model-route revision.
- A configured external runtime can now be exercised by the same state machine as the local runtime without special-case billing or Asset behavior.
- Missing runtimes and mismatched output contracts fail before successful Asset creation; unavailable routes fail before reserving credits.
- Actual vendor adapters, cost reconciliation, content-policy integration, and controlled canaries remain production work rather than being simulated.
