# ADR 0008: Data rights, retention, and delayed deletion lifecycle

## Status

Accepted on August 11, 2026.

## Decision

- A personal data-rights request requires an active session created within 15 minutes, exact confirmation of the account handle, and a rolling request limit. There is no shared-account exception; the same authorization and retention rules apply to every personal account.
- Data export is a durable worker job. It builds an owner-only JSON package, excludes credential/session/network secrets, uses migration 0098 streaming generation and storage parts of at most 5 MiB (not a whole-package limit), stores byte-exact SHA-256 evidence, and expires after seven days.
- Marketplace exports use the same repeatable-read snapshot as the rest of the package. Buyer evidence includes retained contracts, entitlements, payment/refund history and delivery/cleanup evidence; sellers receive their own product configuration and historically attributable sales summaries without buyer identity or private payment details. Explicit projections exclude storage locations, hosted checkout and return URLs, raw Provider payloads and operator recovery notes. Missing historical evidence is never reconstructed from a current listing. See [the marketplace export contract](../resource-marketplace-flows.md#85-个人资源市场交易证据导出).
- Export expiry is executable retention rather than a display-only timestamp: a delayed job purges the artifact body under an explicit database maintenance setting, marks the request complete, and retains checksum/size/time evidence.
- Account deletion is delayed for 30 days and remains owner-cancellable before the deadline. Primary processing revokes sessions/OAuth, removes notifications and owned local media, denies Asset/content access, anonymizes identity and authored content, and preserves minimum transaction, audit, and safety facts.
- Owner exports include requester-visible Support cases, messages, and ordered state evidence while excluding operator identity and assignment metadata. On deletion, Support subject/details, rights statements, message bodies, resolution prose, and event free text are replaced with fixed redaction markers; category, state, timestamps, resource reference, resolution code, and pseudonymous relational integrity remain as minimum operational evidence.
- Support messages and events remain append-only during normal operation. A transaction-local data-rights maintenance setting permits only fixed redaction values while requiring every other row field to remain byte-equivalent, so it cannot be used as a general evidence-editing bypass.
- Completion creates an append-only per-domain receipt. The receipt explicitly reports production backup expiry and external Provider deletion as external boundaries; local execution never claims those systems were erased.
- New receipts explicitly retain marketplace contract/payment/recovery evidence and mark external Providers as `not_erased_by_local_deletion`. This replaces the obsolete claim that no external Providers are configured; existing immutable receipts are not rewritten. Transaction retention periods and field minimization still require a complete retention policy; migration 0098 supplies multipart storage and a complete verified download, while production resource limits remain to be validated.
- `admin:data-rights` controls account-wide legal holds. Authority references are hashed before persistence; creation and release require a reason and explicit confirmation, notify the owner, write Admin audit evidence, and block or requeue deletion. Holds require review within 90 days and expire within 365 days.

Migration 0099 adds evidence-preserving operator recovery for failed export generation and expiry jobs. Queued requests with a failed generation job and no active replacement project as failed; existing ready artifacts remain ready even when worker acknowledgement fails. Recovery requires `admin:data-rights`, confirmation and current eligibility, and never recreates a ready artifact or extends expiry.

Migration 0100 adds guarded recovery for failed account-deletion jobs through the same request-job service and Admin queue. Recovery preserves the raw deletion stage, original grace/cancellation deadlines, legal holds, preparation evidence and immutable failure lineage. Processing means irreversible cleanup, never a renewed cancellation opportunity. Deletion creation/cancellation, legal-hold changes and both worker phases serialize by account before row locks; releasing a hold finds the current blocked request even when its historical optional link is missing or points to a cancelled request. Missing-job reconciliation and production alerting remain pending. See [the recovery scope](../resource-marketplace-flows.md#89-账户删除失败恢复与法律保留串行化0100).

Migration 0101 adds indexes for natural legal-hold expiry. The worker reconciles immediately at startup and once per minute, bounded to 100 records and 10 seconds per pass. Per-account transactions persist expiry, system audit and rescheduling of the current blocked deletion together, preserving the original grace period and rechecking active holds. Busy/failed subjects remain discoverable; a rotating in-memory cursor prevents the oldest batch from monopolizing subsequent passes and resets safely on restart. Only queued deletion jobs suppress a successor: a running handler may already have returned blocked before acknowledgement. Creating a replacement hold expires stale active records without an intermediate deletion resumption. Worker shutdown cancels and awaits maintenance; logs omit private database error text. This covers blocked account deletion, not all deferred media cleanup, missing jobs or production alerting. See [scope and verification](../resource-marketplace-flows.md#810-法律保留自然到期与自动重调度0101).

Migration 0102 adds cleanup reevaluation for ended holds, including historical released/expired rows. Immutable dispatch evidence links each hold/subject to a queued cleanup job while retaining original failures. Product batches commit before account processing; each account step uses its own transaction so dispatch never retains payment locks while waiting for account locks. Durable order/account cursors survive partial failure and restart. Worker expiry and cleanup scans have independent time budgets. Final check audit means reevaluation completed, not media erased; deletion workers still enforce current retention and future holds. Personal exports scope check/dispatch records to the owner or buyer and omit other parties’ hold details. Missing jobs unrelated to ended holds, full legacy reconciliation and production alerting remain outside this checkpoint.

Migration 0103 adds independently snapshotted product-order cleanup reconciliation, without requiring an ended legal hold. Only consistently resolved order/payment states with no retention obligation or active cleanup job qualify. Missing dispatch or a successful no-op may receive a linked successor; failed and cancelled jobs are never reset automatically. Payment locks serialize dispatch, recovery and transaction events; immutable evidence and audit commit with the new job. Workers recheck current funds as well as rights/holds, and operator retries preserve the durable resolved-order requirement across generations. Buyer-only account exports include reconciliation lineage. This does not close generic deleted-account source-media, missing deletion-stage jobs, legacy orders without snapshots or production alerting. See [scope and verification](../resource-marketplace-flows.md#813-独立订单副本遗漏清理与资金复核0103).

Account physical-media cleanup and the deletion finalizer acquire all related product-payment rows in stable ID order before user, product or source-asset locks. This aligns their ordering with fulfillment, refunds and independent delivery cleanup, preventing the reproduced user/asset → payment reverse edge. Relationships derive from accepted contract sources and purchase origins as well as the buyer, not the current listing owner. Existing hold and retention checks remain authoritative; this change does not add generic missing-cleanup reconciliation or a physical-deletion ledger. See [concurrency verification](../resource-marketplace-flows.md#814-账户媒体清理与订单处理的锁顺序).

Migration 0104 reconciles missing deletion jobs only for an original owner-authored request with elapsed execution/cancellation deadlines, consistent preparation state, no receipt and no active hold. Missing jobs or a latest successful no-op qualify; failed/cancelled jobs retain their existing handling. The account lifecycle lock serializes dispatch with cancellation, holds, recovery and execution. Jobs, immutable stage/predecessor evidence and audit commit atomically; worker maintenance has a separate bounded rotating pass. Execution and recovery check the durable request-level evidence across all successor jobs, including hold resumption. Active owners can export only their own dispatch projection; deleted owners cannot obtain exports. Missing consent/stage evidence, generic post-deletion source-media reconciliation, capacity and alerting remain outside this checkpoint. See [scope and tests](../resource-marketplace-flows.md#815-注销请求执行遗漏与阶段证据复核0104).

Original-media cleanup now shares a subject relation covering asset ownership, task grant parties, frozen product contract locations and legacy purchase buyers. After related payment locks, physical cleanup takes the complete subject set in stable ID order and rechecks holds in a fresh statement. Subject locks use `FOR NO KEY UPDATE`: they serialize with hold creation/status changes while permitting foreign-key references to another related account acting as the hold operator. Copy cleanup follows the same lock strength. Account preparation/redaction modifies only that account's own asset metadata. Ended-hold dispatch also follows original-media relations, including legacy orders and task grants with no independent copy. This fixes reproduced cross-account source deletion and hold-operator FK contention; generic original-media reconciliation remains incomplete. See [scope and evidence](../resource-marketplace-flows.md#816-跨账户原件法律保留共享位置与清理锁).

Migration 0105 adds missing original-media cleanup reconciliation for verifiable completed owner deletions, independently of ended legal holds. Dispatch, predecessor linkage and audit commit atomically; failed/cancelled jobs stay operator-controlled. Execution and recovery inherit the original completion-evidence check by account. Only known managed original/frozen locations qualify, subject to the shared rights/hold policy. Cleanup reads at most 100 locations per batch, verifies absence after storage Delete, then writes an immutable receipt and audit in the same transaction. Receipts distinguish removed from already-absent and store a location hash, not the raw key. Failed commits retry idempotently without claiming a prior deletion timestamp. Owner-only exports omit storage locators and foreign actors. The fifth worker maintenance pass has its own budget. API/worker/export/recovery now require 0105; no running development database was migrated. Provider versions, backups, out-of-band restores, unknown objects, inconsistent historical consent, production capacity and alerting remain separate acceptance work. See [scope and tests](../resource-marketplace-flows.md#817-原始媒体遗漏补发与逐文件清理证明0105).

## Consequences

- Export and deletion survive API/worker restarts and expose stable evidence instead of relying on synchronous UI actions.
- A data export cannot leak stored password hashes, session tokens, network hashes, or Admin-only package contents through its API contract.
- Support evidence can satisfy both access and deletion requests without silently retaining the requester's free-form case narrative. A legal hold continues to block the entire deletion transaction before redaction begins.
- Legal preservation is conservative and account-wide in this checkpoint. Production domain-scoped holds require an approved retention inventory and legal operating procedure before replacing this boundary.
- Production release still requires backup inventory/expiry verification, external Provider deletion receipts, outbound communications, and legal review; these remain external acceptance conditions rather than blockers to local lifecycle testing.


## Export resource budgets and nested streaming (2026-09-20)

Exports retain one repeatable-read snapshot and the complete existing JSON schema. Nested support messages/events, email/webhook attempts and refund observations use separate cursors rather than growing per-parent aggregates. Each fetch returns one record, with a server-side serialized-size check before returning bytes to pgx. Generation uses transaction-local 4 MiB work_mem and a 60-second statement timeout within the existing ten-minute job deadline; neither is a claim of a hard database-process memory limit.

Private spools enforce a configurable total-byte budget (default 512 MiB), record budget (8 MiB) and free-space floor (64 MiB). The descriptor is private so alternate write paths cannot bypass limits; read/write/seek honor cancellation and close releases the shared two-slot process budget once. Deterministic size errors stop automatic retries; storage and concurrency failures use bounded retry. Safe resource codes appear in the owner projection and shared operator queue. Any generation failure rolls back artifacts, parts, ready state and notification. A lower download budget never changes a previously accepted artifact or its expiry.

The production template uses a separate size-limited private tmpfs for each API/worker, so capacity planning must include RAM consumed by exports. A free-space observation does not reserve bytes across processes. Role-level database temp-file limits, multi-host quotas, alerts and complete handling of accounts beyond the time/size budgets remain production gates. See [the marketplace audit](../resource-marketplace-flows.md#812-导出资源预算与嵌套历史流式读取).
