# Catalog page components

The task marketplace, community, inspiration library, resource marketplace, asset library, purchased content and orders share the baseline in the root `DESIGN.md`.

- **CatalogToolbar** composes `CatalogStickyBar` and `UiFilterBar`. Supply controls through the default slot and a `filter-class` for page-specific wrapping. Wrap sorting, layout switches and display actions in `.catalog-display` inside `.catalog-controls`. The toolbar detects rendered `.catalog-views`: multiple views keep controls on the right; single/no view places business filters on the left and display controls on the right. A lone display group fills the row, placing sorting on the left and the layout switch on the right (including desktop sidebar pages whose category selector is hidden). Filter-only toolbars (no views or display group, such as orders) align the complete filter group to the right on desktop. Narrow screens wrap groups in reading order. Do not add page-specific alignment flags or margins. Its `resize` event reports the actual controls height, including keyword rows.
- View labels use `catalog.views`: All / Mine / Saved / Following / Drafts / Available. Keep domain names in page headings, search scopes and status announcements.
- **CatalogViews** renders segmented views, selected counts, accessible loading status, and horizontal scrolling that keeps the selected view visible. With fewer than two views, the visible control and its container are omitted; the accessible result-status announcement remains.
- **CatalogKeyword** displays the current keyword and emits `clear`. The page owns the route update, preserving its other filters.
- **CatalogResultSummary** aligns the result count and a quiet information note on one row, wrapping naturally on narrow screens. Pass translated explanatory copy via `note` and the result status through the default slot, retaining loading/error semantics. Orders and workspace tasks share it. An optional localized `note-label` collapses the note into an adjacent information button with hover, keyboard-focus and touch access; Escape and outside interaction dismiss it.
- **CatalogResults** retains the previous results height while loading, preventing scroll clamping and sticky-toolbar jumps. Pass initial-loading state only, not pagination-loading state.
- **CatalogEntry** owns the media/copy/aside layout, responsive list and grid geometry, title/summary typography and native stretched detail link. Use `media`, `meta`, `aside`, and `actions` slots for business fields. Independent links belong in `meta` or `actions`, above the stretched link. Use `has-media=false` for text-only entries. Community, inspiration and resource marketplace use it; task cards keep their budget/status-specific layout.
- **catalog-page.css** is opt-in through `.catalog-page`, and owns header sizes, sidebar surface/offset, tab and control styling. It is loaded by `CatalogToolbar`. Keep field-specific wrapping in page CSS.
- **searchScopes.ts** registers route, scope, labels and icons for the shared header search. Each registered page must read `q` from the URL. Use an optional `matches(route)` predicate for shared routes (the asset scope only applies to `/workspace/assets`, with a separate scope for purchases and no scope on asset detail). Use `maxLength` when the domain has a search limit.

New pages should retain `PageHeader`, `CategoryBrowser`/`UiCategorySidebar`, `UiCatalog`, and existing empty/error/pagination components. Set `--catalog-toolbar-height` from the toolbar's `resize` event. Do not copy shared selectors or add separate context-title bars.

Regression coverage: `community-layout.ui.spec.ts`, `discover-layout.ui.spec.ts`, `marketplace-layout.ui.spec.ts`, and `tasks-experience.ui.spec.ts`. Run with `npx playwright test --config playwright.ui.config.ts <files>` from `web/`.

The asset library combines `AssetLibraryEntry` with `CatalogEntry`; `AssetCatalogViewport` retains bounded rendering, keyboard continuity and visible scan polling. Pass `min-card-width=300` to match catalog grid geometry. Saved counts indicate loaded entries because the API does not provide a total. Keep non-clean previews gated and publication/reuse actions permission-aware.

Local purchased-content fixtures can be populated with `python3 scripts/seed-purchase-examples.py --buyer-id UUID` from the repository root. The script uses the fixed development Docker database, deterministic IDs and preserves existing orders and assets; reruns repair only the exact generated draft product listings. It creates eight labelled assets with zero-dollar test orders and frozen source/license evidence, including a refund-pending and scan-review example; Their active local example listings have separate public preview assets so order product links work. No payment gateway, billing balance or historical order contract is changed.

Orders reuse `CatalogToolbar`, `CatalogKeyword` and `CatalogResults`, with `domain/OrderRecord.vue` for the record hierarchy. Order details use the shared `UiDialog`: transaction, license and event evidence use separate shared `UiTabs` panels inside the modal while the list keeps its height and position. Order-evidence deep links open details; payment returns keep processing feedback visible. The orders API is cursor-only: header search and status/date filters cover loaded records and are labelled accordingly. Their query changes must retain loaded pages and the current payment/refund lifecycle; only navigation outside those filter keys reloads order data.

The workspace task list uses `WorkspaceTaskEntry` with `CatalogEntry` for responsive list/grid records. Its header search, type, status and sort are URL-backed, server-side filters; every page request must retain `mine: true` and the full filter criteria, including cursor retries. Keep `CatalogResults` mounted for loading/error states and preserve the distinction between task budget and earnings.
